## 주요 지적 사항 및 수용 여부

### 1. KOSIS API 직접 사용 지양 → 수용

- **Codex 권고**: CSV 다운로드 → 정적 `data.json`으로 변환하여 사용
- **근거**: API 키 발급, CORS, rate limit 등 부수 부담 발생
- **추가 이점**: 정적 JSON은 git에 commit 가능 → 재현성 확보
- **조치**: Phase 1부터 정적 JSON 방식 채택. `data/` 폴더에 원본 CSV와 변환 결과 함께 저장.

### 2. Phase 2 지도는 시군구 → 시도 단위로 축소 → 수용

- **Codex 권고**: 시군구 단위 choropleth 생략, 시도(17개) 단위만 진행
- **근거**: 시군구 행정구역 코드 통폐합 이슈로 디버깅 시간 과다 소모 우려
- **조치**: Phase 2 스코프를 "시도 단위 choropleth"로 축소. README, design.md 갱신 필요.

### 3. 폐교 지도 레이어 제외 → 수용

- **Codex 권고**: 폐교는 지도 레이어 대신 시도별 카드/차트로 표현
- **근거**: 폐교 데이터는 주소 기반 → 좌표 변환(geocoding) 필요 → Phase 3 일정에 부적합
- **조치**: 폐교는 통계 카드 + 시도별 막대차트로만 표현. 지도 레이어 제외.

### 4. README의 깨진 링크 해결 우선 → 수용

- **Codex 권고**: 존재하지 않는 `docs/design.md`, `docs/requirements.md`, `docs/lessons-learned.md` 먼저 생성
- **근거**: 채점자가 repo 진입 시 깨진 링크는 부정적 인상
- **조치**: design.md는 작성 완료. requirements.md / lessons-learned.md는 stub으로라도 즉시 생성.

### 5. 커밋 메시지 컨벤션 일관 적용 → 수용

- **Codex 권고**: `docs: 설계 문서와 요구사항 초안 추가` 같은 Conventional Commits 형식
- **조치**: 후속 모든 커밋에 일관 적용.

## Lessons Learned (Codex 리뷰로부터)

### Lesson 4: AI는 자신의 제안을 과대평가하는 경향이 있다

Claude는 Phase 2 지도 작업을 1주일로 잡았으나, Codex가 시군구 GeoJSON 처리의 실제 난이도를 더 정확히 평가함. **단일 AI의 일정 추정은 낙관 편향이 있을 수 있다.** 본 과제에서도 두 AI 의견 교차 검증을 통해 보정함.

### Lesson 5: 리스크는 "데이터 소싱"에 가장 먼저 나타난다

초기 설계 시 데이터 소싱은 "구하면 된다" 수준으로 다뤘으나, 실제로는 형식·정합성·좌표 변환 등 부수 작업이 핵심 리스크임. **다음 프로젝트에서는 Phase 0에 "데이터 소싱 가능성 검증"을 명시적 단계로 둘 것.**

### Lesson 6: 비판적 리뷰는 구체적 대안과 함께 와야 가치 있다

Codex가 단순히 "지도 위험함"이 아니라 "시도 단위로 축소", "폐교는 차트로" 등 **구체적 대안**을 제시했기 때문에 즉시 의사결정 가능했다. AI에게 리뷰를 요청할 때는 *"문제 지적 + 대안 제시"*를 함께 요구하는 프롬프트가 효과적임.
