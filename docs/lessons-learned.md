# Lessons Learned

본 문서는 프로젝트를 진행하며 얻은 소프트웨어공학 및 AI 보조 개발 교훈을 누적 기록한다.

---

## 2026-05-18: 주제 선정과 AI 교차 검증

### Lesson 1: 무난한 앱은 보고서 소재가 약할 수 있다

플래시카드, 습관 트래커, 가계부는 CRUD 구조가 명확하지만 요구사항 분석과 스코프 조정 과정이 단조롭다.
지역 불균형 대시보드는 데이터 소싱, 시각화 범위, 지도 난이도 같은 의사결정 지점이 많아 소프트웨어공학 과정을 설명하기에 더 적합했다.

### Lesson 2: AI도 리뷰 대상이어야 한다

Claude의 초기 제안을 Codex가 비판적으로 검토하면서 더 적합한 주제로 수렴했다.
단일 AI 답변을 그대로 따르기보다, 역할을 나누고 교차 검증하면 편향과 낙관적 추정을 줄일 수 있다.

### Lesson 3: MVP는 기능 목록이 아니라 탈출 경로다

지도와 폐교 레이어가 막혀도 카드와 차트만으로 제출 가능한 결과물을 확보해야 한다.
따라서 Phase 1은 통계 카드와 막대차트로 제한하고, 지도는 Phase 2로 분리했다.

## 2026-05-21: 문서 정합성과 구현 착수

### Lesson 4: 문서 링크도 품질이다

README가 존재하지 않는 문서를 가리키면 프로젝트의 신뢰도가 떨어진다.
초기 단계라도 요구사항, 테스트 계획, 회고 문서의 최소 골격을 먼저 만들어야 한다.

### Lesson 5: 데이터 소싱은 구현보다 먼저 리스크가 된다

API 직접 연동은 키, CORS, 호출 제한, 응답 변경 문제를 만든다.
과제 목적상 정적 JSON을 기준으로 구현하고, 출처와 임시값 여부를 명시하는 편이 더 안정적이다.

### Lesson 6: 스코프 축소는 실패가 아니라 관리다

시군구 지도와 폐교 위치 레이어는 매력적이지만 일정 대비 위험이 크다.
시도 단위 지도와 폐교 차트로 축소한 결정은 기능 포기가 아니라 일정과 품질을 보호하는 요구사항 관리다.

## 2026-05-25: 소프트웨어공학 프로세스 명시화

### Lesson 7: 프로세스는 머릿속에 있으면 증빙이 아니다

요구사항 분석, 설계 결정, 구현, 검증, 회고가 실제로 수행되었더라도 문서 간 연결이 약하면
평가자는 개발 과정의 흐름을 따라가기 어렵다. 따라서 `docs/process.md`를 추가하여 방법론,
프로세스 다이어그램, 시퀀스 다이어그램, 산출물 추적성을 한 문서에 정리했다.

### Lesson 8: Markdown 파일도 독자를 위한 UI다

문서가 여러 개로 나뉘면 작성자는 구조를 알지만 처음 보는 사람은 어떤 파일부터 읽어야 할지 모른다.
README에 문서 읽는 순서를 추가하니 요구사항, 설계, 테스트, 회고의 역할이 더 명확해졌다.

### Lesson 9: 수동 테스트만 있으면 재현성이 약하다

브라우저 수동 확인은 필요하지만, 데이터 구조처럼 반복 확인 가능한 항목은 자동화하는 편이 낫다.
`tests/verify-data.mjs`를 추가해 17개 시도, 필수 요약 카드, 수도권 분류를 자동 검증하도록 했다.

### Lesson 10: 지도 데이터는 원격 의존성을 줄여야 한다

Leaflet 지도는 외부 GeoJSON URL을 바로 호출해도 빠르게 구현할 수 있지만, 제출용 프로젝트에서는
재현성이 더 중요하다. 시도 경계 TopoJSON을 `data/`에 고정하고 라이선스를 함께 보관하니,
지도 구현과 데이터 출처 증빙을 동시에 확보할 수 있었다.
