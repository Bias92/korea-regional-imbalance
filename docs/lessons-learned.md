# Lessons Learned

본 문서는 프로젝트를 진행하며 얻은 소프트웨어공학 및 AI 보조 개발 교훈을 누적 기록한다.

---

## 2026-05-18: 주제 선정과 AI 교차 검증

### Lesson 1: 무난한 앱은 보고서 소재가 약할 수 있다

플래시카드, 습관 트래커, 가계부는 CRUD 구조가 명확하지만 요구사항 분석과 스코프 조정 과정이 단조롭다.
지역 불균형 대시보드는 데이터 소싱, 시각화 범위, 지도 난이도 같은 의사결정 지점이 많아 소프트웨어공학 과정을 설명하기에 더 적합했다.

### Lesson 2: AI도 리뷰 대상이어야 한다

Claude의 초기 제안을 Codex가 비판적으로 검토하면서 더 적합한 주제로 수렴했다.
단일 AI 답변을 그대로 따르기보다, 역할을 나누고 교차 검증하면 편향과 낙관적 추정을 줄일 수 있다.

### Lesson 3: MVP는 기능 목록이 아니라 탈출 경로다

지도와 폐교 레이어가 막혀도 카드와 차트만으로 제출 가능한 결과물을 확보해야 한다.
따라서 Phase 1은 통계 카드와 막대차트로 제한하고, 지도는 Phase 2로 분리했다.

## 2026-05-21: 문서 정합성과 구현 착수

### Lesson 4: 문서 링크도 품질이다

README가 존재하지 않는 문서를 가리키면 프로젝트의 신뢰도가 떨어진다.
초기 단계라도 요구사항, 테스트 계획, 회고 문서의 최소 골격을 먼저 만들어야 한다.

### Lesson 5: 데이터 소싱은 구현보다 먼저 리스크가 된다

API 직접 연동은 키, CORS, 호출 제한, 응답 변경 문제를 만든다.
과제 목적상 정적 JSON을 기준으로 구현하고, 출처와 임시값 여부를 명시하는 편이 더 안정적이다.

### Lesson 6: 스코프 축소는 실패가 아니라 관리다

시군구 지도와 폐교 위치 레이어는 매력적이지만 일정 대비 위험이 크다.
시도 단위 지도와 폐교 차트로 축소한 결정은 기능 포기가 아니라 일정과 품질을 보호하는 요구사항 관리다.

## 2026-05-25: 소프트웨어공학 프로세스 명시화

### Lesson 7: 프로세스는 머릿속에 있으면 증빙이 아니다

요구사항 분석, 설계 결정, 구현, 검증, 회고가 실제로 수행되었더라도 문서 간 연결이 약하면
평가자는 개발 과정의 흐름을 따라가기 어렵다. 따라서 `docs/process.md`를 추가하여 방법론,
프로세스 다이어그램, 시퀀스 다이어그램, 산출물 추적성을 한 문서에 정리했다.

### Lesson 8: Markdown 파일도 독자를 위한 UI다

문서가 여러 개로 나뉘면 작성자는 구조를 알지만 처음 보는 사람은 어떤 파일부터 읽어야 할지 모른다.
README에 문서 읽는 순서를 추가하니 요구사항, 설계, 테스트, 회고의 역할이 더 명확해졌다.

### Lesson 9: 수동 테스트만 있으면 재현성이 약하다

브라우저 수동 확인은 필요하지만, 데이터 구조처럼 반복 확인 가능한 항목은 자동화하는 편이 낫다.
`tests/verify-data.mjs`를 추가해 17개 시도, 필수 요약 카드, 수도권 분류를 자동 검증하도록 했다.

### Lesson 10: 지도 데이터는 원격 의존성을 줄여야 한다

Leaflet 지도는 외부 GeoJSON URL을 바로 호출해도 빠르게 구현할 수 있지만, 제출용 프로젝트에서는
재현성이 더 중요하다. 시도 경계 TopoJSON을 `data/`에 고정하고 라이선스를 함께 보관하니,
지도 구현과 데이터 출처 증빙을 동시에 확보할 수 있었다.

### Lesson 11: 시각화는 해석을 대신해주지 않는다

지도와 차트를 띄우는 것만으로는 사용자가 다음 행동을 알기 어렵다.
"어느 지역이 왜 위험한가"를 보여주기 위해 종합 위험지수와 핵심 진단 카드를 추가했다.
데이터 시각화 앱은 수치를 보여주는 것에서 끝나지 않고, 판단 기준을 함께 제공해야 한다.

## 2026-05-26: 분석 기준을 사용자가 바꾸게 하기

### Lesson 12: 점수는 산식까지 보여줄 때 설득력이 생긴다

고정 위험지수만 제공하면 앱이 임의로 순위를 정하는 것처럼 보인다.
균형, 인구감소 중심, 소멸위험 중심, 폐교 중심 시나리오를 추가하니 사용자가
"어떤 기준으로 위험하다고 보는가"를 직접 비교할 수 있게 되었다.

### Lesson 13: 상호작용은 기능 수보다 판단 흐름이 중요하다

버튼을 많이 넣는 것보다 버튼을 눌렀을 때 핵심 진단, 지도, 상세 패널, 위험도 상위 목록이
함께 갱신되는 것이 더 중요했다. 같은 데이터라도 사용자의 판단 흐름에 맞춰 연결되면
단순 조회 화면에서 분석 도구에 가까워진다.

### Lesson 14: 비교 기능은 사용자의 질문을 앱 안으로 끌어온다

지도와 순위는 전체 흐름을 보여주지만, 사용자가 실제로 궁금해하는 질문은 "A 지역과 B 지역은
얼마나 다른가"인 경우가 많다. 두 지역 비교 모드를 추가하니 사용자가 직접 가설을 세우고
위험지수, 인구 흐름, 폐교 수 차이를 확인할 수 있게 되었다.

## 2026-05-27: 파생 지표의 설명 가능성 보강

### Lesson 15: 계산 근거가 보이지 않으면 기능도 단순 표시처럼 보인다

위험지수, 시나리오, 지역 비교가 있어도 산식이 화면에 없으면 사용자는 "앱이 무엇을 판단하는지"를
즉시 알기 어렵다. 위험지수 산식과 가중치 바를 UI에 추가하니 점수의 근거가 드러나고,
데이터 조회 화면에서 설명 가능한 분석 도구로 한 단계 가까워졌다.

### Lesson 16: 문서의 요구사항 ID는 기능의 안전장치다

산식 설명 UI를 `FR-017`로 분리해 요구사항, 설계 결정, 테스트 계획에 연결하니 작은 기능도
프로세스 산출물 안에서 추적된다. 바이브코딩 결과를 제출용 프로젝트로 만들려면 코드 변경보다
"왜 추가했고 어떻게 검증했는가"를 함께 남겨야 한다.

## 2026-05-29: 임시 데이터를 공식 통계로 교체하기

### Lesson 17: 데이터 교체는 한 번에 다 바꾸지 말고 단위를 쪼개라

`phase1-regions.json` 전체(summary + 17개 시도)를 한 번에 공식 데이터로 바꾸려 하면
검증 부담이 크고 어디서 틀어졌는지 추적이 어렵다. 화면 최상단 요약 지표 4종만 먼저
교체하니 변경 범위가 작아 출처 확인·값 검증·테스트가 모두 명확해졌다. 큰 데이터 교체일수록
"가장 눈에 띄고 검증 가능한 작은 단위"부터 잘라 가는 것이 프로세스 관리에 유리하다.

### Lesson 18: 숫자보다 출처가 신뢰성을 만든다

값을 공식 통계로 바꾸는 것만으로는 부족했다. 각 지표에 `source`, `sourceYear` 필드를
추가해 카드에 출처가 직접 보이게 하니, 같은 숫자라도 "어디서 온 값인가"가 드러나
대시보드가 단순 표시 화면에서 근거 있는 분석 도구로 한 단계 올라섰다. 데이터 시각화에서는
값 자체보다 값의 출처와 기준연도를 함께 보여주는 것이 신뢰성의 핵심이다.

### Lesson 19: 확실하지 않은 값은 억지로 바꾸지 않는 것도 의사결정이다

폐교 누계는 출처별(보유폐교/종결폐교 포함 여부, 집계 시점)로 값이 크게 달라 단일 공식
수치를 특정하기 어려웠다. 무리하게 새 숫자로 교체하는 대신 값은 유지하고 출처만 명시한 뒤
"단일 기준연도 누계 확정"을 후속 과제로 분리했다. 불확실성을 숨기지 않고 문서에 남기는 것도
데이터 프로젝트에서 정당한 의사결정이다.

## 2026-05-31: 기능 확장과 회귀 방지

### Lesson 20: 데모 기능은 사용자의 조작 동선으로 평가된다

지역 목록이 상위 6개 고정일 때는 정보는 있었지만 사용자가 직접 탐색한다는 느낌이 약했다.
검색, 권역 필터, 정렬을 추가하니 같은 데이터라도 사용자가 질문을 만들어 확인할 수 있게 되었다.
대시보드의 기능성은 화면 개수보다 사용자가 바꿔볼 수 있는 판단 기준의 수에서 드러난다.

### Lesson 21: 자동 검증은 데이터뿐 아니라 UI 계약도 지켜야 한다

정적 HTML 앱은 빌드 단계가 없기 때문에 DOM id 하나가 바뀌어도 런타임에서야 문제가 드러날 수 있다.
`verify-ui-contract.mjs`로 핵심 컨트롤과 렌더링 함수 연결을 검사하니, 기능이 늘어도 최소한의
회귀 방지선을 만들 수 있었다.

## 2026-06-01: 보고서 전환 준비

### Lesson 22: 제출물은 앱과 문서 사이의 간극에서 흔들린다

앱 기능이 늘어도 최종 보고서가 그 흐름을 따라가지 못하면 평가자는 개발 과정을 재구성해야 한다.
보고서 요약 MD 다운로드와 `final-report-draft.md`를 추가하니 화면 상태, 요구사항, 설계 결정,
검증 결과를 하나의 제출 논리로 묶을 수 있게 되었다.

### Lesson 23: 자동으로 만들어지는 요약도 한계를 함께 써야 한다

보고서 요약 기능이 핵심 수치만 내보내면 임시 데이터 문제를 흐릴 위험이 있다. 따라서 생성되는
Markdown에 데이터 한계와 위험지수의 성격을 함께 넣었다. 분석 자동화는 결론뿐 아니라 불확실성도
자동으로 드러내야 한다.

## 2026-06-02: 제출 증빙 정리

### Lesson 24: 제출 요구사항은 별도 추적표로 관리해야 한다

기능, 요구사항, 설계, 테스트 문서가 모두 존재해도 과제 요구사항과 직접 연결되어 있지 않으면
평가자는 증빙을 직접 찾아야 한다. `docs/submission-evidence.md`를 추가해 과제 문항과 저장소
산출물을 일대일로 연결하니, 프로세스 적용 자체가 더 명확한 제출물로 바뀌었다.

### Lesson 25: 화면 캡처도 형상 관리 대상이다

최종 PDF에 들어갈 이미지를 로컬에만 두면 어떤 화면을 기준으로 논술했는지 재현하기 어렵다.
대시보드 캡처를 `docs/assets/screenshots/`에 커밋하면 코드, 문서, 화면 증빙이 같은 시점의
형상으로 묶인다. 제출용 프로젝트에서는 스크린샷도 단순 결과물이 아니라 품질 증빙이다.

### Lesson 26: 데모는 보기보다 조작 가능성이 중요하다

지도와 카드가 많아도 사용자가 값을 바꿔 결과를 확인할 수 없으면 "그냥 보여주는 앱"처럼 느껴진다.
정책 대응 시뮬레이터를 추가하니 사용자가 지역과 정책 투입 강도를 직접 바꾸며 위험지수 변화 가설을
확인할 수 있게 되었다. 바이브코딩으로 빠르게 만든 기능일수록 요구사항, 산식, 한계 문구, 테스트를
함께 붙여야 제출용 소프트웨어 산출물로 설득력이 생긴다.

### Lesson 27: 앱이라는 말은 배포 형태까지 설명해야 한다

브라우저에서 실행되는 웹앱과 앱스토어에 올라가는 네이티브 앱은 다르다. 최종 산출물은 정적 웹앱이지만
PWA manifest와 service worker를 추가하면 사용자는 앱처럼 설치해 사용할 수 있다. 제출 문서에서는
"네이티브 앱은 아니지만 PWA로 설치 가능한 웹앱"이라고 구분해 설명해야 오해를 줄일 수 있다.
