# 설계 결정 기록 (Design Decisions)

본 문서는 프로젝트 진행 중 내려진 주요 설계 결정과 그 근거를 기록한다.
ADR(Architecture Decision Record) 형식을 단순화한 형태로 작성한다.

## DD-001: 프레임워크 미사용, Vanilla 스택 채택

- **결정일**: 2026-05-18
- **상태**: Accepted

### 맥락

소프트웨어공학 과제 "프로세스에 입각한 바이브코딩의 효과 논술"의 실증 프로젝트로 데이터 시각화 웹 대시보드를 개발한다. 프레임워크 선정 시 다음 후보를 검토했다.

1. React + Recharts
2. Next.js + D3
3. Vanilla HTML/CSS/JS + Chart.js + Leaflet

### 결정

**3번 (Vanilla 스택)** 채택.

### 근거

| 평가 항목 | Vanilla | React + Recharts | Next.js + D3 |
|---|---|---|---|
| 초기 설정 비용 | 낮음 | 중간 | 높음 |
| Git 커밋 가시성 | 높음 (정적 파일) | 낮음 (빌드 산출물) | 낮음 (빌드 산출물) |
| 보고서 캡처 적합성 | 높음 | 높음 | 높음 |
| AI 도구 안정성 | 높음 (버전 충돌 없음) | 중간 | 중간 |
| 학습 곡선 | 낮음 | 중간 | 높음 |
| MVP 도달 속도 | 빠름 | 중간 | 느림 |

핵심 판단:
- 본 과제의 평가 핵심은 **결과물 품질이 아닌 프로세스 적용 증빙**이다.
- 프레임워크 설정 시간만큼 프로세스 문서화에 투자하는 것이 더 합리적.
- 정적 파일 기반이면 `index.html`, `app.js` 등의 변경 이력이 git history에 직관적으로 남아 채점자가 진행 과정을 따라가기 쉽다.

### 결과

- 빌드 도구 없이 브라우저에서 바로 실행 가능한 구조 채택
- 외부 라이브러리는 CDN으로 로드
- Phase 2에서 Leaflet 도입 시에도 동일 원칙 유지

## DD-002: AI 도구 역할 분담 (Claude × Codex)

- **결정일**: 2026-05-18
- **상태**: Accepted

### 맥락

과제 요건상 바이브코딩 AI 도구는 자율 선정 가능하다. 단일 AI 사용 vs 복수 AI 교차 사용을 검토했다.

### 결정

**Claude + Codex 병행 사용, 역할 분담 운용**.

| 도구 | 주 담당 |
|---|---|
| Claude | 요구사항 정리, 문서/보고서 작성, 의사결정 토론, 코드 리뷰 |
| Codex | 코드 구현, 버그 수정, 비판적 리뷰, 커밋 메시지 정리 |

### 근거

- 단일 AI 사용 시 그 AI의 편향이 그대로 결과물에 반영되는 리스크 존재
- 킥오프 단계에서 이미 효과 확인: Claude의 1차 주제 제안(플래시카드)을 Codex가 반박하여 더 적합한 주제(지역 불균형 대시보드)로 수렴함
- 두 AI의 응답 비교 자체가 **lessons learned의 핵심 소재**가 됨

### 결과

- 주요 의사결정 시 두 AI 의견을 모두 청취 후 결론 기록
- 모든 교차 토의는 `docs/ai-log/` 폴더에 날짜별로 누적
- 최종 보고서에 "단일 AI vs 교차 검증" 비교 섹션 포함 예정

## DD-003: Phase 기반 점진 개발 + MVP 우선

- **결정일**: 2026-05-18
- **상태**: Accepted

### 맥락

21일이라는 제한된 기간 내에 데이터 시각화 대시보드를 완성해야 한다. 데이터 시각화는 스코프 크리프 위험이 큰 영역이다.

### 결정

4단계 Phase 구조 채택, 각 Phase 종료 시점에 산출물 검증.

| Phase | 목표 | 기간 |
|---|---|---|
| 1 (MVP) | 통계 카드 + 막대차트 | 2026-05-18 ~ 05-24 |
| 2 | Leaflet 시도 단위 지도(choropleth) | 2026-05-25 ~ 05-31 |
| 3 | 폐교 통계 + 필터 + 설명 카드 | 2026-06-01 ~ 06-05 |
| QA / 보고서 | 버그픽스, PDF 작성 | 2026-06-06 ~ 06-08 |

### 근거

- MVP를 Phase 1 끝에 확보하면 이후 Phase가 막혀도 제출 가능한 결과물이 존재
- 지도 시각화(Phase 2)는 난이도가 높아 MVP에서 제외
- 각 Phase 종료 시점이 자연스러운 회고 지점이 되어 lessons learned 누적에 유리

### 결과

- Phase 1 완료 전까지 지도 작업 착수 금지
- Phase 2 지도는 시군구가 아닌 시도 단위로 제한
- 폐교 데이터는 지도 레이어가 아니라 카드와 차트로 표현
- 각 Phase 종료 시 `docs/ai-log/`에 회고 기록

## DD-004: API 직접 호출 대신 정적 JSON 데이터 채택

- **결정일**: 2026-05-21
- **상태**: Accepted

### 맥락

Phase 1 대시보드는 KOSIS, 행정안전부, 교육부 등 여러 출처의 데이터를 함께 사용한다. 브라우저에서 API를 직접 호출하는 방식은 API 키 발급, CORS, 호출 제한, 응답 형식 변경 리스크를 동반한다. 과제의 핵심은 실시간 데이터 연동이 아니라 소프트웨어공학 프로세스 적용과 시각화 산출물이다.

### 결정

**원본 CSV를 확보한 뒤 전처리된 정적 JSON을 `data/`에 저장하여 사용한다.**

### 근거

- 정적 JSON은 Git에 커밋할 수 있어 결과 재현성이 높다.
- 브라우저 보안 정책과 외부 API 장애에 영향을 덜 받는다.
- Phase 1의 구현 범위를 카드와 막대차트에 집중할 수 있다.
- 데이터 변환 과정 자체를 문서화하면 요구사항 추적과 검증이 쉬워진다.

### 결과

- Phase 1은 `data/phase1-regions.json`을 기준 데이터로 사용한다.
- 원본 CSV를 확보하면 `data/raw/`에 보관하고, 변환 결과는 `data/processed/` 또는 루트 JSON으로 관리한다.
- 데이터 값의 출처와 임시값 여부는 README 또는 별도 데이터 문서에 명시한다.

## DD-005: 위험 기반 반복·점진 개발 프로세스 채택

- **결정일**: 2026-05-25
- **상태**: Accepted

### 맥락

본 프로젝트는 단기간 과제이며, 기능 구현뿐 아니라 소프트웨어공학 프로세스 적용을 증빙해야 한다.
데이터 시각화 프로젝트 특성상 데이터 확보, 지도 구현, 폐교 위치 전처리 등 일정 리스크가 크다.

검토한 접근은 다음과 같다.

1. 선형 폭포수 모델
2. 완전한 애자일 스프린트 모델
3. 위험 기반 반복·점진 개발

### 결정

**위험 기반 반복·점진 개발**을 채택한다.

각 Phase는 작은 단위의 `요구사항 -> 설계 -> 구현 -> 검증 -> 회고` 흐름을 따른다.
단, 전체 프로젝트는 Phase 1 MVP, Phase 2 지도, Phase 3 폐교 통계 확장으로 점진적으로 확장한다.

### 근거

- 폭포수 모델만 사용하면 초기 요구사항 변경과 데이터 소싱 리스크에 대응하기 어렵다.
- 완전한 애자일 스프린트는 1인 과제 규모에 비해 의식과 산출물이 과하다.
- 반복·점진 개발은 제출 가능한 MVP를 먼저 확보하면서도, 지도와 공식 데이터 교체를 후속 Phase로 관리하기 좋다.
- V-Model식 추적성을 함께 적용하면 요구사항과 테스트 기준을 명확히 연결할 수 있다.

### 결과

- `docs/process.md`에 전체 프로세스와 다이어그램을 추가한다.
- 새 기능은 요구사항과 설계 결정 기록을 먼저 갱신한 뒤 구현한다.
- 각 Phase 종료 시 `docs/ai-log/`와 `docs/lessons-learned.md`에 회고를 남긴다.
- 자동화 가능한 검증은 `tests/`에 스크립트로 누적한다.

## DD-006: Phase 2 지도 경계는 저장소 내 TopoJSON으로 관리

- **결정일**: 2026-05-25
- **상태**: Accepted

### 맥락

Phase 2 목표는 시도 단위 choropleth 지도다. Leaflet은 GeoJSON과 잘 맞지만, 원본 시도 GeoJSON은
파일 크기가 커서 정적 대시보드에 부담이 된다. 반대로 외부 URL을 매번 호출하면 네트워크 상태와
원격 파일 변경에 영향을 받는다.

### 결정

`southkorea/southkorea-maps`의 KOSTAT 2018 시도 단위 단순 TopoJSON을 `data/`에 저장하고,
브라우저에서는 `topojson-client`로 GeoJSON으로 변환한 뒤 Leaflet에 전달한다.

### 근거

- 단순 TopoJSON은 원본 GeoJSON보다 작아 정적 호스팅에 적합하다.
- 경계 파일을 저장소에 포함하면 제출 시점의 화면을 재현하기 쉽다.
- 데이터 출처와 라이선스를 `data/README.md`와 `data/skorea-provinces-license.md`에 남길 수 있다.
- Phase 2는 시군구가 아니라 시도 단위이므로 17개 경계만 있으면 MVP 요구를 충족한다.

### 결과

- `data/skorea-provinces-2018-topo-simple.json` 추가
- `src/app.js`에서 Phase 1 지역 데이터와 지도 경계 코드를 매핑
- 지도 상세 패널에 인구 증감률, 인구감소지역 수, 폐교 수 표시
- 지도 지표 전환과 지역 선택 인터랙션 추가
- `tests/verify-data.mjs`에서 지도 경계 17개와 코드 매핑을 자동 검증
